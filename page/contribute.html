01 / Prepare

A raw task is four things.

Put them in a folder. This is everything we need from you — no metadata schema, no verifier, no instruction files.

  • buggy_workspace/
    The run that broke

    Complete code that reproduces the defect, plus that run's own artifacts — left where the run wrote them.

  • fixed_workspace/
    The run that worked

    The same tree with the defect repaired, plus its own run. The two must differ only by the fix; anything else that differs is something the comparison is also measuring.

  • Dockerfile
    Where they ran

    Pin the versions, and say in a comment which recorded run they came from.

  • README.md
    What you found

    The defect, the fix as a diff, and the measured outcome of both arms.

Keep the artifacts

The wandb offline directory, the full command-line output, and every per-step metric file. Those are what a threshold gets calibrated against.

Leave it raw

Absolute paths, hostnames and broken/fixed labels in your logs are expected. Sanitizing them is step 02.

Say how many runs

One run per side supports margins, not variance. Whoever sets the threshold needs to know which you have.

raw_task_example

A Search-R1 GRPO run whose retriever returns an all-zero query vector.

Every document scores 0.0, so the same three documents come back for every question. Nothing raises.

02 / Package

An agent builds the task.

The repo ships a package-task skill. Point an agent at your raw task and it produces the directory above — one workspace instead of two, the fix sealed into the oracle, assets moved into prepare.sh, your Dockerfile mapped onto a shared image, and the logs sanitized and thinned.

Prompt
Use the package-task skill to turn raw_tasks/<my_task> into an
AutoRLBench task under tasks/. Read its README.md for the defect,
the fix, and the measured results of both runs. Ask me for anything
the README does not already answer.

It finishes by running the structural validator, which must report zero errors.

03 / Submit

Open a pull request.

Against the main repository, with the generated task. Keep the raw task out of the PR unless it is small enough to be useful as evidence. An idea or a half-built case is also welcome as an issue — we would rather see it early than not at all.

What it becomes

Two levels

Your raw task becomes one or both of these. Issue is a diagnosis. Solution is that same diagnosis plus a run that applies the fix. A bundle with both workspaces supports both; without a repaired run, it stops at Issue.

Before you publish

Run the same checks the catalog will run.

Resolve every structural error locally, then exercise both evaluation levels with a known-good fixture.

  1. 01
    Freeze the case

    Capture the workspace, environment, configuration, logs, and held-out evidence.

  2. 02
    Replay both sides

    Run the grader against each recorded run: the broken one must fail and the repaired one must pass. This is the only offline check a threshold gets.

  3. 03
    Validate and exercise

    Run the structural validator and test each verifier against a known result.

Structural validation
PYTHONDONTWRITEBYTECODE=1 \
python3 -m autorlbench validate path/to/your_task

A task is ready for the catalog when the command passes and its public workspace is usable offline.
